Prompt-to-Design

AI that only builds from real components

Concept Project AI-UX Design

Note: A concept-stage prototype covering three states, not a shipped tool. Sole designer, with Claude as a thinking partner. Scope was deliberately held to three components — Card, Input and Button.

Overview

Most “prompt-to-design” tools generate a screen the same way every time: type something, get back a layout, colors and components invented on the spot. This project starts from a narrower, harder question — what if the AI could only build with components that already exist in your system, and had to show its work while doing it?

Service

AI-native product thinking taken from problem framing through to interaction design: defining the constraint, designing the three states that carry it, and writing the interface copy that makes the constraint read as a feature.

Problem

Designers and PMs drafting a new screen often either don’t know the component library well enough to reuse what’s there, or reach for a generic AI tool that invents new colors, spacing and components from scratch — quietly introducing inconsistency into the system. What’s missing isn’t an AI that can generate UI. It’s a way to describe a screen in plain language and get back something assembled only from real, existing components, with full visibility into exactly which ones were used.

So the tool had to do three things:

  • Take a plain-language description of a screen
  • Assemble it only from components already in the system
  • Show which components it used, as it used them

Approach

The strongest decision in this project wasn’t a screen — it was rejecting the obvious framing. “AI that generates UI from text” is the generic, forgettable version every AI design tool already claims. The real problem isn’t generation, it’s governance: making sure what gets generated is provably consistent with a system that already exists. Once that reframe was in place, every design decision followed from one question — how do you make “on-system” visible, not just true?

Process

Three states, in the order a user meets them. Each one has a single job in making the constraint legible.

01

Describe the screen you need

The prompt sets the constraint before the user even starts typing — placeholder copy reads “Build only from your existing design system — 3 components available.” A suggestion chip gives a fast starting point for someone who’d rather not write a prompt from scratch. The goal here is small but specific: make the constraint read as a feature, not a limitation, before a single character is typed.

02

Thinking, made legible

Instead of a plain loading state, the build narrates itself — Using Card… Using Input… Using Button… — announcing each component as it’s pulled in. This is the most differentiated screen in the project: it turns a black box into an audit trail. The user isn’t just waiting for output, they’re watching the system prove, one component at a time, that it never left the library it was given.

03

Your screen is ready

The result renders next to a “Components used” breakdown — a plain tally of what was drawn from the system to build the screen. A refine action lets the user adjust the description and regenerate, rather than hand-edit the result, keeping iteration inside the same on-system loop instead of drifting outside it.

Why the transparency step matters

Design systems don’t usually fail because people ignore them — they fail quietly, one slightly-off spacing value or unregistered variant at a time, in ways nobody notices until much later. Surfacing component usage as it happens turns “on-system-ness” into something the tool proves continuously, rather than something a reviewer has to catch after the fact. That’s the actual idea behind this project: not the finished screen, but the thinking in between.

What this is (and isn’t)

This is a concept-stage prototype covering three states, not a shipped tool. There’s no live connection to a real component library, design token pipeline or plugin API behind it, and three components is illustrative, not a claim of scale. What it’s meant to demonstrate is judgment: that AI-native design tooling should be evaluated less on how good its output looks, and more on whether it can show its work.

What’s next

The natural next layer of this idea is handling the cases where the system doesn’t have a clean answer:

Inexact-match transparency — if a prompt implies something the system doesn’t have (a stepper control, say), the tool says so instead of silently substituting: “No exact match for ‘stepper control’ — using Input/Number as the closest available component.”

A human checkpoint — a “flag for review” action on any screen where an inexact match was used, so AI-assisted output still gets a human decision before it ships, not just before it’s trusted.

Further out — show the real component list next to the prompt box, not just in the placeholder text. Connect the tool to an actual token and component registry instead of the fixed three-item stand-in. And build it as working software — a Figma plugin or agent workflow — instead of designed screens.
